# 01 · 内置助手架构：把 Agent 做成应用的一等公民

> **TL;DR**
> TvEHub Community 的助手不是一个外挂聊天框，而是应用内的原生窗口，由两条循环组成：
> **前端 LLM 决策循环**负责理解意图、选择命令、组织参数；**Rust 确定性大脑**
> 负责检索、拆解、门控、记账与进化。模型只“提议”调用，真正的执行权在本地
> 后端的决策中心。知识在构建期内嵌、工坊资源在运行时同步，所以助手不必每次
> 从零认识这个应用。

---

## 1. 问题：为什么“聊天框 + 一堆宏”走不远

把一个 LLM 接进编辑器，最容易的做法是：

1. 在界面右下角放一个聊天框；
2. 在提示词里塞几十条“你可以调用 X”；
3. 模型输出一段 JSON，前端 `eval` 或 `switch` 一下，直接调内部函数；
4. 出错就让用户重试。

这个做法在演示里能跑，但一旦任务变长就会暴露四个结构性问题：

- **能力没有单一事实源。** UI 一套实现、助手一套实现、远程控制再一套，三套行为
  迟早分叉。
- **执行没有边界。** 模型可以直接改内存、写文件，绕过撤销、格式校验和权限。
- **上下文没有预算。** 二十几轮工具调用后，历史膨胀，弱模型开始复读、空回、
  反复重载同一份资料。
- **知识没有沉淀。** 每次会话都从零开始，用户上次纠正过的做法不会变成下一次的
  默认策略。

TvEHub Community 的助手架构就是为了解决这四件事：**能力原子化、执行后端化、上下文预算化、
知识内嵌化**。

## 2. 总体拓扑

助手是一个独立的 Tauri 窗口，label 为 `assistant`，由 Rust 在首次打开时创建
（无边框浮动面板，默认 680×720），入口在首页标题栏。它不是浏览器扩展，也不是
外部子进程，和编辑器共享同一个应用进程、同一份配置根、同一套后端能力。

```text
┌──────────────────────────── 应用进程 ────────────────────────────┐
│                                                                  │
│  ┌────────────────────┐        ┌──────────────────────────────┐  │
│  │ 助手窗口 assistant  │        │ 编辑器窗口 editor-*          │  │
│  │                    │        │                              │  │
│  │ AssistantChat.vue  │        │ 命令注册表 + 场景镜像         │  │
│  │  ├ 语言归一化       │        │  ├ node.* / scene.* / asset.* │  │
│  │  ├ brain.decompose │        │  └ devtools:cmd 执行器        │  │
│  │  ├ runAgent 循环    │        └──────────────▲───────────────┘  │
│  │  └ 工具执行器       │                       │ Tauri 事件        │
│  └─────────┬──────────┘                       │ devtools:cmd      │
│            │ invoke                            │                   │
│            ▼                                   │                   │
│  ┌─────────────────────────────────────────────┴───────────────┐  │
│  │ Rust 后端                                                    │  │
│  │  ai_chat_stream（LLM 流式代理）                              │  │
│  │  Brain（知识图谱 / NLU / 策略 / 台账 / 审批）                 │  │
│  │  brain_execute（决策中心：门控 → 内部 devtools 通道 → 观测）  │  │
│  │  devtools 内部通道（require_tool → 本地直答 / 编辑器执行）    │  │
│  └──────────────────────────────────────────────────────────────┘  │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

这里有三条容易被忽略的设计约束：

- **助手窗口不执行编辑器写操作。** 它没有引擎实例，也不直接持有场景。所有
  `node.*` / `scene.*` 都要转到活跃编辑器窗口执行。
- **LLM 外呼在 Rust。** 前端不直接 `fetch` 供应商，而是调 `ai_chat_stream`；
  流式增量经 `ai:chunk` 事件回推，结束/失败经 `ai:done` / `ai:error` 回推。
  供应商方言（思考参数、工具调用增量、`content` 数组形态）集中在后端适配。
- **执行权在 Rust。** 前端 `execAssistantTool` 只调 `brain_execute`，门控和
  派发都在后端完成。模型即使被提示词注入，也只能“请求”一个已登记的方法。

### 2.1 窗口内部组成

| 模块 | 职责 |
| --- | --- |
| `AssistantApp.vue` | 两栏布局：左栏项目工作区/文件树，右栏聊天与设置；窗口位置恢复 |
| `AssistantChat.vue` | 发送管线、时间线、流式气泡、思考条、停止按钮、黄灯确认浮动条 |
| `NluSteps.vue` | 语义单元化动态块：轨迹 + 单元状态（running/ok/fail） |
| `ToolSteps.vue` / `timeline.ts` | 工具调用与结果的静态回放（历史会话） |
| `conversations.ts` / `runs.ts` | 会话存储与按会话隔离的运行态 |
| `refs.ts` / `fileidx.ts` | `@` 引用解析与大文件模块索引 |
| `inline-tools.ts` / `tool-dialects*.ts` | 无原生 function-calling 时的正文调用解析与方言清洗 |
| `skills/` | 精简技能注册表（领域 5 + 工作流 3） |
| `nl-normalize.ts` / `nlu.ts` | 语言归一化前置层、单元计划注入 |
| `loadable-index.ts` | 系统提示词里的文档/工坊资源目录 |

这个拆分让“视图”和“运行”解耦：切换设置面板、切换会话、窗口失焦都不会中断
任务；`runs.ts` 里的 `RunState` 跟着启动任务的会话走，而不是跟着当前组件走。

## 3. 两条循环：LLM 负责提议，大脑负责裁决

### 3.1 前端 LLM 决策循环

`src/assistant-window/agent.ts` 的 `runAgent` 是一个工具调用循环：

```text
assembled messages + tools
        │
        ▼
  LLM 流式回复 ──有 tool_calls?──否──▶ 收尾/救援判定
        │是
        ▼
  同一轮并行执行所有工具调用
        │
        ▼
  结果按调用顺序回喂（tool 消息 / 内联文本）
        │
        └──────────────▶ 下一轮（最多 24 轮）
```

它做了几件超出“while(true) 调工具”的事：

- **原生 function-calling 优先，正文方言兜底。** 服务端带 `tools` 下发；若端点
  以 400/422 拒绝 `tools` 字段，后端自动去掉 `tools` 重试一次，前端再用内联
  解析器识别正文里的调用（独立 JSON、`<invoke>`、`<tool_call>`、各家标记模板）。
- **同轮并行、按序回喂。** 无依赖的调用可以同一轮并发执行；结果按调用顺序写回，
  保证 `tool_call_id` 配对不乱。
- **上下文预算。** 供应商配置 `contextK`（千 token，默认 128），预算按
  `K × 1024 × 1.5` 字符估算；单条工具结果上限随预算放大（默认 4000 字符，
  最高 64K）；最近 6 批结果保全文，更早的只留头部。
- **弱模型护栏。** 重复加载短路、同参数连败短路、空回复续跑、行动宣言救援、
  “零工具就宣称完成”守卫、格式纠偏、整批复读暂停。这些不是“让模型更聪明”，
  而是让它在不可靠时**不要空转**，并把暂停变成显式、可恢复的状态。
- **跨轮进度备忘。** 历史持久化时会丢弃工具结果（避免服务端拒绝没有
  `tool_calls` 的 `tool` 消息），所以发送前会把本会话已成功的写操作压成一行
  备忘注入 wire；用户说“继续”时，还会回放上一任务的结果头部，避免从头重跑。

### 3.2 Rust 确定性大脑

`src-tauri/src/brain/` 是一个不调用 LLM 的本地策略层。它的输入是任务文本、方法名、
执行结果；输出是检索命中、任务拆解、门控决策、观测记账。

```text
任务文本
   │
   ├─ brain_query      语义检索技能/命令/概念
   ├─ brain_plan       生成执行计划 + 门控决策
   ├─ brain_decompose  语义单元化（分段 → 检索 → 命令预测）
   ├─ brain_execute    单次工具调用的门控与派发
   └─ brain_observe    执行结果回写（台账 + 因果链 + 自动维护）
```

大脑的主体状态在一把 `Mutex` 后面（文件内模块索引另有独立锁），操作都是微秒到
毫秒级的内存操作；图谱主体的磁盘写入只发生在维护 tick 的 gzip 快照原子替换。这个选择让“每调一个工具就问一次大脑”变得可行——
如果大脑本身要调 LLM，它就会变成第二个不确定源，也会把每次调用的延迟和成本翻倍。

## 4. 一次任务的完整时序

以“创建一个项目，加一个旋转方块，导出单页网页”为例：

```text
用户输入
   │
   ▼
① 语言归一化（可选，LLM 单轮）
   normalizeNaturalLanguage → NormSpec
   { taskType, task, keywords, files }
   失败/超时 → null，后面按原文走规则链路
   │
   ▼
② 大脑拆解（确定性，微秒级）
   brain_decompose(text, root, spec)
   → 分段 → 每段图谱检索 → 命令预测 → TaskUnit[]
   → direct 单元（仅无参绿灯查询）由大脑直接执行
   → assist 单元合并为一次助手会话
   │
   ▼
③ 助手会话
   runAgent(messages = 原文 + 知识命中 + 执行计划)
   → LLM 返回 tool_calls
   → execAssistantTool
        │
        ▼
④ 决策中心（Rust）
   brain_execute({ task, method, params })
   → 行动三区判定
   → 黄灯且任务未批准 → needConfirm（不执行）
   → 批准后重发 → 放行
   → devtools 内部通道（require_tool → 本地直答 / 编辑器执行）
   → 观测回写（台账 + 因果链）
   │
   ▼
⑤ 编辑器执行
   devtools:cmd → handleMethod → runCommand → 命令实现
   → 场景后端提交 / 文件写入 / 预览 / 构建
   │
   ▼
⑥ 结果回喂
   { result } 或 { error } → LLM 自纠 → 下一轮
   │
   ▼
⑦ 收尾
   模型输出最终总结；用户可在时间线看到每个工具步骤
```

关键点在 ③ 和 ④ 之间：**LLM 的“决定”不是“执行”。** `needConfirm` 是后端
返回的状态，不是模型说了算；用户拒绝后，前端会把“用户拒绝执行”作为错误回喂，
模型只能改方案或终止，不能绕过。

## 5. 大脑内部：一个会遗忘、会压缩、会进化的本地知识网络

### 5.1 数据模型

节点分五类：

| 类型 | 含义 | 生命周期 |
| --- | --- | --- |
| `Skill` | 领域技能（操作手册、脚本模板、交付纪律） | 常驻热层 |
| `Command` | 可执行方法（`node.add`、`asset.write`…） | 常驻热层 |
| `Concept` | 概念/词元/文档基图元/工坊资源 | 常驻热层 |
| `Task` | 一次任务回合 | 情景记忆，可冷却下沉 |
| `Outcome` | 一次执行结果 | 情景记忆，可冷却下沉 |

边分四类：`Mentions`（技能→概念）、`Uses`（技能→命令）、`Caused`（任务→命令→
结果）、`CoOccurs`（概念共现）。边权在 `0..1`，按 14 天半衰期衰减，低于 `0.02`
在维护 tick 中修剪；被观测强化的边先衰减再增益，封顶 1.0。

因果链 `CausalChain` 记录一次任务的事件序列。它让“这个任务通常怎么走”从一次
会话里留下来，而不是只留在聊天记录里。

### 5.2 向量与自压缩

语义检索不依赖外部 embedding 服务。`vector/embed.rs` 用字符级特征（ASCII 词元 +
CJK 单字/二元组）做 FNV-1a 哈希，散到 128 个桶，L2 归一；`vector/quant.rs` 再做
i8 对称量化，每个向量约 136 字节（128 个桶值 + 模长 + 特征数）。余弦用 i32 点积，
量化噪声对排序基本无感。

选择哈希嵌入而不是本地神经网络，是一个明确的取舍：路由只需要“任务文本 ↔ 技能
描述”的粗粒度相似，哈希嵌入零依赖、O(len)、结果确定，能耗比拉一个本地模型低两个
数量级。它不擅长开放域语义，但对“找这个应用里该用哪个命令”足够。

维护 tick 每 25 次观测自动触发一次：

```text
衰减修剪因果边 → 向量近重复合并（图重定向）→ 情景节点冷却下沉（最多 8 个）
→ 因果链裁剪 → gzip 快照原子落盘
```

“向量自压缩”不是比喻：近重复向量会合并，边和链改挂到保留节点，热层只留高频
结构，冷层按需提升。这样长期使用不会让图谱无限膨胀。

### 5.3 效能台账与 0.99 门

`metrics::OutcomeLedger` 按方法记录尝试次数、成功次数、总耗时；`policy::budget`
计算效能比：

```text
正确率 = 拉普拉斯平滑(成功, 尝试, 先验 40 次 @ 0.995)
速度分 = min(1, 方法速度预算 / 实际平均耗时)
能耗分 = min(1, 能耗预算 / (耗时 × 区域权重))
效能比 = 正确率 × (0.5 × 速度分 + 0.5 × 能耗分)
```

自主执行门槛是 `0.99`。冷启动没有历史时按先验 0.995 放行，避免“第一次什么都不敢
做”；20 次里错 1 次会降到 0.98，之后的计划就需要确认。这个门不是安全门，而是
**可靠性门**：它决定“这类操作历史上够不够稳，能不能不再打扰用户”。安全边界由
[05 权限门](05-permission-gate.md) 负责，两者不要混为一谈。

需要精确区分：`brain.plan` 用效能比决定整任务是 `autoExecute` 还是
`NeedConfirm`；单次 `brain_execute` 的门控只看行动三区与审批会话，不拿效能比
直接放行或拒绝一次写操作。这样“历史不稳”只会让计划更保守，不会让某次危险操作
因为“以前没失败过”而被放行。

## 6. 语言归一化与语义单元化：把“自然语言”变成“可检索、可执行的小任务”

### 6.1 语言归一化前置层

`src/assistant-window/nl-normalize.ts` 在发送前做一次单轮 LLM 结构化：

```json
{
  "taskType": "operate | create | optimize | analyze | chat",
  "task": "规范化后的一句话任务",
  "keywords": ["node.add", "旋转", "tween"],
  "files": ["src/TweenMotion.ts"]
}
```

它只做四件事：消除口语歧义、提取检索锚点、判断任务类型、列出提到的文件。文件
只对工作区清单做**存在性校验**，绝不读取内容；提取到的路径对不上工作区就全部
剔除。任何失败（无供应商、20 秒超时、输出不合法）都返回 `null`，大脑按原文走
既有规则链路——这一层对下游是透明的，不能成为单点故障。

### 6.2 语义单元化

`brain_decompose` 是确定性的：

```text
任务文本（规范化后）
   │
   ├─ 分段（标点/连接词）
   ├─ 每段图谱检索（技能/命令/概念）
   ├─ 命令预测（图谱命中优先，词典兜底）
   ├─ 阶段判定（inspect / act / verify）
   └─ 执行模式判定
        ├─ direct：仅“无参绿灯查询”四种
        │   editor.state / project.list / scene.list / asset.list
        └─ assist：其余全部交给助手细化
```

`direct` 的存在不是为了炫技，而是为了省掉不必要的模型推理：用户说“列出资产”，
大脑直接调 `asset.list` 并回填结果，零 LLM 往返。除此之外，写操作、带参操作、
模糊表述一律走 `assist`——助手负责把自然语言转换成精准方法名与参数，但最终仍
经决策中心门控。

还有两个细节：

- **知识命中只给目录，不预载全文。** 每段最多 4 条技能/文档/工坊资源，工坊资源
  保底最多 2 个名额；注入的是“这是什么 + 用哪个工具取”，全文由
  `load_skill` / `load_doc` / `load_repo` 按需拉取。
- **隐式依赖补齐。** 如果任务里有 `node.add` 但没有 `project.open`，会自动插入
  一个“在编辑器中打开项目”的 assist 单元。用户说“在项目中加一个方块”时通常
  不会说“先打开项目”，这个补齐把常见的失败路径提前消掉。

### 6.3 合并为一次会话

所有 `assist` 单元不会各自开一次会话，而是合并成**一次**助手运行：单元计划作为
路线图注入，模型在单个工具循环里按序推进。逐单元独立会话会让全量上下文往返
N 倍，这是“通信慢”的主因。只有全部单元都是 `direct` 时，才零 LLM 完成并直接
汇总结果。

## 7. 知识层：构建期内嵌 + 运行时同步

助手需要知道三件事：这个应用怎么用、SDK 怎么写、有没有现成范例。

| 知识 | 来源 | 进入方式 |
| --- | --- | --- |
| 技能 | `.agents/skills/` | `build.rs` 生成 `skills_index.json`，`include_str!` 内嵌二进制 |
| 官方文档 | `public/docs/` | `build_docs.rs` 生成 `docs_index.json`，内嵌为 `Concept` 节点 |
| 工坊原型 | `public/repos/` | 运行时扫描，按仓库指纹懒刷新（2 秒节流），无需重编译 |
| 前端技能子集 | `src/assistant-window/skills/` | 8 条精简技能（领域 5 + 工作流 3），`load_skill` 直接用 |

系统提示词里常驻**可加载资料索引**（id + 标题 + 摘要），而不是全文。这样弱模型
第一次调 `load_doc` / `load_repo` 就能带对 id，不需要用空参试探、靠报错回喂目录
自纠——每个任务省 1~2 轮。

工坊资源是动态层：外部改文件后，最迟在下一次读路径的指纹检查窗口中入图，不需要
重新编译应用。这让“工坊里新加的原型”能立刻成为助手可参考的知识。

### 7.1 `@` 引用与大文件

用户可以在输入框里 `@` 一个项目文件。小文件直接作为附件注入；大文件走
`file.index`：按标题/窗口切分模块、生成摘要、向量化并落盘缓存，发送时只注入
模块目录，模型需要细节时再用 `file.search`（摘录）或 `file.module`（单模块全文）。
这条通道解决的是“不要把整个大文件塞进上下文”，也是上下文预算之外的另一层
按需加载。

## 8. 会话与运行态：切走再切回，任务不丢

- **会话是数据，不是界面状态。** 会话存在配置根 `assistant/conversations/`：
  `index.json` + 每会话 `conv-<id>.json`，原子写（临时文件 + rename）。早期把
  会话塞进 `ui-state` 时，窗口重启时序可能在加载完成前用空副本覆盖索引，导致
  全部会话丢失；独立目录把事故影响面收窄到单文件。
- **运行态按会话隔离。** `runs.ts` 用 `Map<convId, RunState>` 保存 `busy`、
  流式文本、思考文本、在途请求 id、停止标记、待确认计划、语义单元动态块、黄灯
  确认队列。切换会话不会中断任务，流式增量仍写回启动任务的那个会话。
- **审批队列合并。** 同批并行调用产生的多个黄灯请求会合并为一次裁决；用户批准
  后登记任务审批会话，同任务后续黄灯调用在 10 分钟内直接放行。

---

## 9. 为什么这是“一等公民”，而不是“插件”

把上面的设计放在一起，可以看到五个判据：

1. **同进程、同窗口体系。** 助手是 `assistant.html` 原生窗口，不是外部浏览器或
   扩展；它和编辑器共享配置、主题、会话存储。
2. **同能力面。** 助手调用的方法就是 TCP/MCP 暴露的方法，最终落到同一个命令
   注册表；没有“助手专用后门”。
3. **同执行权。** 模型只提议，Rust 决策中心裁决；权限门、格式锁、路径检查都在
   执行侧，不在提示词里。
4. **同知识源。** 技能和文档在构建期内嵌，工坊资源运行时同步；助手不需要每次
   从零学习这个应用。
5. **同验证闭环。** 预览、截图、保存、构建都是命令；助手可以自己验证结果，用户
   也能在时间线和调用日志里复核。

这也是它与“屏幕自动化 Agent”最根本的区别：后者靠“看”和“点”，前者靠“语义
调用”和“可审计执行”。

补充一句范围：外部 Agent 工具也可以不装成插件，直接通过开发者服务的 TCP 接口
接入编辑器；那是一条独立的外部接入路径，能力面与权限门见
[02 TCP 指令集](02-tcp-command-set.md) 与 [03 两套协议](03-dual-protocols.md)。
本文讲的是应用内的内置助手。

## 10. 边界与限制

如实列出当前实现的边界，避免把架构读成营销：

- **LLM 仍然是外部依赖。** 助手需要用户配置 OpenAI 兼容供应商；没有供应商时，
  大脑的检索/拆解/门控仍可用，但自然语言对话与参数生成不可用。
- **大脑是确定性的词法/图检索，不是通用语义模型。** 它对“这个应用里该用哪个
  命令”有效，对开放域推理不在行；语言归一化层正是为了弥补口语化输入。
- **弱模型护栏是启发式。** 复读检测、宣言救援、完成语义判断都基于规则，可能
  误判；设计上给它们设置了预算和显式暂停，宁可暂停也不静默死循环。
- **助手不能做未登记的事。** 能力面就是方法表；方法表里没有的能力，助手无论
  怎么“想”都调不到。这是特性，不是缺陷。
- **上下文预算依赖供应商配置正确。** `contextK` 填小了会过早裁历史，填大了可能
  被供应商截断；默认 128K 是保守值。
