# 07 · 差异与创新：护城河是约束系统，不是模型

> **TL;DR**
> 如果按单点看，命令模式、知识图谱、MCP、撤销栈、权限门都早有先例。TvE Hub 的
> 差异不在“发明了某个原语”，而在**把这些原语按同一条执行链组合起来**：一张能力面
> 同时服务 UI、外部 Agent 和内置助手；执行权收归本地后端；确定性大脑负责策略与
> 学习，LLM 只负责语言；五道门分层约束；最终由构建管线交付真实产物。
>
> 本文把“市面上没有”改成一个可检验的说法：**在公开方案里少见的组合**。每条断言
> 都给出代码证据和验证方式，读者可以自己判断。

---

## 1. 先划清“创新”的口径

我们不把下面这些当成创新，因为它们都有成熟先例：

| 原语 | 先例 |
| --- | --- |
| 命令模式 / 命令注册表 | 编辑器、IDE、游戏引擎的 command system |
| 撤销/重做栈 | 几乎所有编辑器 |
| 知识图谱 / 向量检索 | 语义搜索、RAG、推荐系统 |
| MCP | Anthropic 提出的 Agent 工具互操作标准 |
| JSON Lines / JSON-RPC | 通用协议 |
| 权限门 / 工具开关 | 操作系统权限、IDE 扩展权限 |
| 本地小模型/规则 NLU | 传统 NLP、专家系统 |

所以本文说的“创新”，指的不是“第一个做出某个功能”，而是下面三件事：

1. **结构组合**：这些原语被放在同一条执行链上，彼此约束，而不是各自为政。
2. **职责切分**：谁提议、谁裁决、谁执行、谁验证，边界清楚且可审计。
3. **可交付性**：系统最终产出的是可运行、可部署的产物，不是一次演示。

---

## 2. 常见形态与它们的断点

下面按“形态”而非具体产品比较，避免把某家公司当成靶子。每种形态都有强项，也都有
结构性的断点。

| 常见形态 | 强项 | 结构性断点 | TvE Hub 的补位 |
| --- | --- | --- | --- |
| 代码生成型 Agent（IDE 内或独立） | 生成/修改代码快、生态成熟 | 主要交付物是代码或文本；应用状态、撤销、构建验证通常由用户或外部脚本补 | 命令直接作用于应用状态，写后有撤销、格式校验和构建产物 |
| 屏幕操作型 Agent（Computer Use） | 不依赖应用提供 API，什么界面都能试 | 靠像素与坐标，语义弱、易碎；无法保证原子性、权限和撤销 | 语义方法调用，不点坐标；权限与校验在执行侧 |
| MCP 工具桥 / 插件式集成 | 标准、易接、宿主现成 | 常常是“一个工具包一个 API”，缺少统一命令面、统一撤销和统一策略 | 方法表 + 命令中心；MCP 只是适配层，不是第二套实现 |
| 引擎内置 AI 助手 | 与编辑器深度集成，懂领域 | 多为闭源/云端/插件形态；外部 Agent 难复用同一能力面 | 本地开发者服务 + 双协议；内置助手与外部 Agent 共享方法表 |
| 低代码 / 原型生成器 | 上手快、演示效果好 | 停在原型层；状态模型、格式校验、导出管线往往不完整 | 真实项目、真实场景后端、真实构建管线 |
| 传统编辑器脚本 / 宏 | 确定、可重复 | 需要人写脚本，不懂自然语言，不会规划 | 自然语言入口 + 确定性大脑 + 同一命令执行 |

这些断点可以归成一句话：**大多数方案只优化“生成”或“操作”中的一层，缺少从语义
到执行、从执行到产物、从产物到审计的闭环。**

## 3. 八个结构性差异

### 3.1 一张能力面，三种消费路径

**是什么。** UI（工具栏/快捷键/右键菜单）、外部 Agent（TCP/MCP）、内置助手，最终
都落到同一张方法表和同一套执行实现（前端命令注册表 / Rust 本地执行器）。

```text
UI ───────────────┐
外部 Agent ─ TCP/MCP ─┼──▶ 方法表 ──▶ 命令注册表 / Rust 本地执行器
内置助手 ─ 进程内通道 ─┘
```

**为什么。** 如果每个入口各写一套实现，行为迟早分叉：同一个“删除节点”，UI 会
检查根节点，Agent 不会；UI 走撤销，Agent 直改 JSON。分叉之后，权限和审计都会出现
盲区。

**带来什么。**
- 新增能力只实现一次，所有入口同时获得；
- 权限、格式锁、调用记录只有一个挂载点；场景写撤销在命令路径上统一；
- 换协议不改能力，换模型不改行为。

**代码证据。** `src/app/commands/registry.ts`、`src/app/lib/devtools/state.ts`
（`METHOD_TO_COMMAND`）、`src/app/lib/devtools/handlers.ts`。

---

### 3.2 执行权后端化：模型提议，后端裁决

**是什么。** 内置助手的每次**编辑器操作**工具调用都先到 Rust 的 `brain_execute`：
行动三区判定、任务审批、工具权限、再派发。前端 LLM 只“提议”方法与参数，不能自己
执行。`load_skill` / `load_doc` / `load_repo` 与 `brain.plan/query/stats` 是只读的
知识/咨询通道，不走执行门控。

```text
LLM 输出编辑器工具 tool_call
  → brain_execute（Rust）
      → 绿灯：直接执行
      → 黄灯且未批准：返回 needConfirm，不执行
      → 红灯/未登记：拒绝
      → 执行后 observe 回写
```

**为什么。** 提示词是模型可影响的内容，不是安全边界。把裁决放在模型进程里，等于
让被约束者自己决定是否越界。执行权必须在模型接触不到的地方。

**带来什么。**
- 提示词注入无法直接变成写操作；
- 模型不能“自我批准”；
- 拒绝/确认会计入大脑决策计数，执行调用会进统一日志。

**代码证据。** `src-tauri/src/brain/execute.rs`、`src-tauri/src/brain/policy/zones.rs`、
`src/assistant-window/tools.ts`（`execAssistantTool` → `api.brainExecute`）。

---

### 3.3 确定性大脑与 LLM 分工

**是什么。** 路由、拆解、门控、记账、知识维护由 Rust 大脑完成，不调 LLM；LLM 只
用于理解自然语言、生成参数、编写脚本/内容。

**为什么。** 如果“该用哪个命令”也要问 LLM，就会引入第二个不确定源，并把每次工具
调用的延迟和成本翻倍。大脑需要的是可重复、可测试、微秒级。

**带来什么。**
- 同样的图谱状态与任务文本得到可重复的检索/拆解结果；
- 离线可用，不依赖供应商；
- 观测结果能直接变成策略：边权衰减、冷热分层、效能比；
- LLM 的职责收窄到它真正擅长的地方。

**代码证据。** `src-tauri/src/brain/`（`mod.rs`、`nlu/`、`graph/`、`vector/`、
`policy/`）；嵌入是字符级哈希，不依赖外部 embedding 服务。

---

### 3.4 语义单元化与绿色直执行

**是什么。** 任务先被拆成单元：`direct` 单元（仅无参绿灯查询）由大脑直接执行，
零 LLM 往返；`assist` 单元合并成一次助手会话，按计划推进。

**为什么。** 用户说“列出资产”时，让模型思考三轮再调 `asset.list` 是浪费。反过来，
所有任务都直执行又会绕过语言理解。按“是否死板、是否有明确方法”分流，比统一走
LLM 更省、更稳。

**带来什么。**
- 确定性查询零 LLM 成本；
- 模糊任务只开一次会话，避免逐单元 N 倍上下文往返；
- 计划作为路线图注入，弱模型不容易迷路。

**代码证据。** `src-tauri/src/brain/nlu/mod.rs`（`DIRECT_NO_ARG`、`ExecMode`）、
`src/assistant-window/AssistantChat.vue`（direct/assist 分流）、
`src/assistant-window/nlu.ts`（计划注入）。

---

### 3.5 五道拦截门与路径差异化

**是什么。** 网络安全、能力开关、行动三区、数据边界、引擎校验五道拦截门，外加
审计台账；内置助手有逐动作批准，外部 Agent 没有，但共享工具权限与格式/引擎校验。

**为什么。** 把权限做成一个布尔值，只能在“全开很危险”和“全关不能用”之间选。
分层门让每一层回答不同的问题：谁能连、能调什么、能写哪里、能写成什么样、出了事
怎么查。

**带来什么。**
- 读操作不打扰用户，写操作可批准；
- 外部自动化不被逐动作确认卡死；
- 格式锁与引擎校验对所有入口一致；
- 审计可归因到方法和来源。

**代码证据。** `src-tauri/src/devtools.rs`（`require_tool`、`locked_write_reason`、
`scene_write_of`、`shader_write_of`）、`src-tauri/src/brain/policy/zones.rs`、
`src-tauri/src/brain/execute.rs`。

> 这里有一个容易被误读的点：外部 Agent 共享的是“执行架构”，不是“助手决策架构”。
> 详见 [05 权限门](05-permission-gate.md) 第 4 节。

---

### 3.6 双协议同源

**是什么。** TCP JSON Lines 与 MCP 同属开发者服务，共用同一端口、同一方法表、同一
工具权限和同一调用记录。MCP 是适配层，不是第二套实现。

**为什么。** 只做 MCP，内置助手会被外部协议的版本和形态绑住；只做 TCP，标准宿主
接不进来。两套协议、一套能力，是“生态兼容”和“原生控制”的折中。

**带来什么。**
- 外部 Agent 工具可以直接用 TCP，标准宿主用 MCP；
- 新增方法不需要写两遍；
- 协议适配只做翻译，不做业务。

**代码证据。** `src-tauri/src/devtools.rs`（`dispatch_command`、`resolve_mcp`）、
`src-tauri/src/bin/mcp.rs`、`src/app/lib/devtools/state.ts`。

---

### 3.7 从指令到产物的闭环

**是什么。** 场景权威状态在 Rust，写操作有撤销历史；预览可截图；构建管线产出
`build/web/` 或单页 `index.html`；编辑器与导出运行时消费同一份 RHI/RPI 源码。

**为什么。** 演示型 Agent 的终点通常是“生成一段代码/一张截图”，用户还要自己
运行、调试、导出。产物型 Agent 的终点应该是“一个可以直接打开或部署的东西”。

**带来什么。**
- 场景操作可回滚，失败可重试；
- 写前有格式校验，项目不容易被写坏；
- 画面语义在编辑器和产物之间一致；
- Agent 可以用截图/构建结果自验，而不是“说完成了”。

**代码证据。** `src-tauri/src/scene/history.rs`、`src/framework/scene/SceneClient.ts`、
`src-tauri/src/build/`、`src-tauri/src/preview.rs`、`src/engine/rhi/`、
`src/engine/rpi/`、`src/runtime/runtime/stage.ts`。

---

### 3.8 可审计、可进化、弱模型可用的运行工程

**是什么。** 统一调用日志（最近 50 条，区分助手/控制端）、大脑决策计数、成效台账、
因果链、冷热分层；前端 Agent 循环有上下文预算、重复调用短路、空回复续跑、行动
宣言救援、零工具完成守卫、方言解析与进度备忘。

**为什么。** 真实用户不会总用最强模型。一个只在“强模型 + 原生 function-calling +
大上下文”下能跑的架构，在便宜模型、本地模型、网关方言下会迅速退化。可靠性要
做进运行工程，而不是指望模型“更聪明”。

**带来什么。**
- 弱模型也能完成多步任务，卡住时显式暂停而不是静默空转；
- 外部 Agent 的每次调用可归因（开发者服务 `call_log`）；
- 内置助手路径的执行结果会回写大脑，更新策略，越用越稳；外部 Agent 的调用目前
  只进 `call_log`，不进大脑台账；
- 长会话不容易因为上下文膨胀而失忆/复读。

**代码证据。** `src/assistant-window/agent.ts`、`src-tauri/src/brain/metrics.rs`、
`src-tauri/src/brain/graph/causal.rs`、`src-tauri/src/brain/store/`、
`src-tauri/src/devtools.rs`（`call_log`）。

## 4. 为什么这样设计：六条第一性原理

1. **Agent 需要语义 affordance，而不是像素。** 屏幕自动化能“看”，但看不到
   “节点/组件/撤销/权限”这些语义；命令面才是 Agent 的原生接口。
2. **安全必须在执行侧，不能在提示词里。** 提示词可以被注入，执行侧的门不会。
3. **能确定的地方不要用 LLM。** 路由、拆解、记账、门控用确定性代码；LLM 只做
   语言理解和内容生成。
4. **能力面与协议解耦。** 协议会变，能力不该跟着变；MCP 是投影，不是本体。
5. **产物需要权威状态 + 校验 + 构建。** 只有“生成”没有“执行/验证/导出”，就还是
   演示。
6. **弱模型是常态，不是异常。** 运行工程要能在不可靠的模型上优雅降级，而不是
   假设模型永远听话。

## 5. 与“给编辑器加一个 AI 助手”的结构对比

| 维度 | 常见“加 AI”方案 | TvE Hub |
| --- | --- | --- |
| 能力来源 | 助手专用 API / 提示词里的宏 | 与 UI、外部 Agent 共用的方法表 |
| 执行位置 | 助手进程 / 前端直调 | Rust 决策中心 + 命令中心 |
| 状态权威 | 前端内存 / 文件 | Rust 场景会话 + 撤销历史 |
| 写前校验 | 提示词劝告 / 少量校验 | 格式锁 + 引擎同款解析/反序列化 |
| 撤销 | 多数没有 | 每条场景命令一次撤销 |
| 外部接入 | 另写一套工具/插件 | TCP/MCP 同一能力面 |
| 知识 | 每次从零提示 | 技能/文档内嵌 + 工坊资源运行时同步 |
| 学习 | 无 / 仅日志 | 台账 + 因果链 + 冷热分层 |
| 验证 | 截图猜 | 预览 + 截图 + 构建产物 |
| 交付物 | 代码/演示 | 可部署的 Web 产物 |

## 6. 哪些不是创新，别自嗨

为了不让这篇文章变成营销材料，明确列出入围“不是创新”的项：

- **MCP 不是我们发明的。** 我们做的是把它作为开发者服务的一个适配层。
- **JSON Lines / JSON-RPC 不是新协议。** 选择它们是因为简单、可调试、生态现成。
- **命令模式、撤销栈、知识图谱、向量检索、权限门都有先例。** 我们的工作是把它们
  放在同一条执行链上，并让约束互相咬合。
- **“AI 助手进编辑器”本身不新。** 新的是它和外部 Agent 共享能力面、执行权在
  后端、并且能走到产物。
- **不是所有写操作都走命令中心。** `asset.write` / `scene.write` / `shader.write`
  是受控文件通道；它们有格式校验，但没有场景撤销历史。
- **外部 Agent 不受行动三区约束。** 这是当前边界，不是隐藏特性；如果要让外部
  Agent 也走助手策略门，需要新增一条受门控的外部执行路径。

把这些写清楚，读者才能判断哪些是真正的结构差异，哪些只是实现选择。

## 7. 可验证的断言

创新点如果不可以验证，就只是叙事。下表给出每条断言的代码证据与检查方式：

| 断言 | 代码证据 | 怎么验证 |
| --- | --- | --- |
| UI、外部 Agent、助手共用一张方法表 | `METHOD_TO_COMMAND`、`handlers.ts`、命令注册表 | 新增一个方法，检查三个入口是否都可见/可调 |
| 助手编辑器工具执行前经过后端门控 | `brain/execute.rs` 的 `gate` 与 `approve_task` | 单测：绿灯自动、黄灯需批准、红灯拒绝、未登记不放行 |
| 权限门在外部入口同样生效 | `devtools.rs` 的 `require_tool`、`locked_write_reason` | 关闭工具/写非法路径/写坏 `.scene`，观察拒绝文案 |
| TCP 与 MCP 同源 | `dispatch_command`、`resolve_mcp`、`mcp.rs` | 同一方法分别用 TCP 和 MCP 调用，比较结果 |
| 场景写有撤销 | `scene/history.rs` 的 `SceneCmd` | 建/删/改节点后 undo/redo，检查状态 |
| 编辑器与产物同渲染语义 | `src/engine/rhi/`、`src/engine/rpi/`、`stage.ts`、`RendererManager` | `pnpm check:layers`；对比预览与构建产物 |
| 外部 Agent 操作可审计 | `call_log`、`devtools_recent_calls` | 外部调用后看首页「最近调用」 |
| 弱模型护栏可测 | `agent.ts` 的守卫与 `*.spec.ts` | 跑 `pnpm test:unit` 相关 spec |

## 8. 对不同读者的意义

**对用户。** 你得到的不是“AI 帮我写了一段代码”，而是“AI 在我的项目里完成了操作，
我能撤销、能看记录、能导出产物”。这两件事的信任成本完全不同。

**对集成者。** 你不必为内置助手和外部 Agent 写两套工具；方法表就是契约。外部
Agent 走 TCP/MCP，内置助手走进程内通道，行为一致，权限边界可配置。

**对贡献者。** 新增能力时，先想“它是不是一个原子命令”，再想“它属于哪个区域、
哪个工具、哪个协议暴露”。这套约束会让代码增长得慢一点，但不会长成互相绕过的
分支。

---

## 9. 结论

模型会换、供应商会换、协议版本会换。真正留下来的是：

- 一张稳定的能力面；
- 一条可审计的执行链；
- 一套分层的安全边界；
- 一个能自验、能交付的产物闭环。

如果只用一句话概括这篇文档：

> **别人让 Agent “看起来会操作”，TvE Hub 让 Agent “真的能操作，并且操作得起、
> 退得回、交得出”。**
